\section{Introduction}

L'analyse lexicale est la première étape d'un compilateur : elle découpe le texte source en
unités significatives (mots-clés, identificateurs, nombres, opérateurs\ldots). Plutôt que de
programmer cet automate à la main, on le décrit avec des \emph{expressions régulières} et
l'outil \textbf{Flex} génère le code C correspondant.

L'objectif de ce TP est de se familiariser avec Flex à travers trois séries d'exercices :
\begin{itemize}[leftmargin=1.5em]
  \item reconnaître les éléments d'un petit langage de programmation (exercice 1.1) ;
  \item utiliser des variables C et des états dans les actions pour supprimer les commentaires (exercice 1.2) ;
  \item écrire des expressions régulières pour quatre langages sur l'alphabet $\{a,b\}$ ou les lettres (exercice 1.3).
\end{itemize}

Tous les exercices sont aussi regroupés dans un seul programme avec un menu
(\texttt{tp3\_menu.l}), ce qui permet de les tester facilement les uns après les autres.

\section{Rappel : fonctionnement de Flex}

Un fichier Flex comporte trois zones séparées par \texttt{\%\%} :

\begin{code}
(definitions : options, macros, code C entre %{ et %})
%%
expression_reguliere     { action en C }
%%
(code C : main, fonctions annexes)
\end{code}

Flex lit le texte et applique deux principes qu'il faut bien avoir en tête pour comprendre
tous les résultats de ce TP :

\begin{idee}[Les deux règles de décision de Flex]
\begin{enumerate}[leftmargin=1.5em,nosep]
  \item \textbf{Plus longue correspondance} : parmi toutes les règles, Flex choisit celle qui reconnaît le plus de caractères.
  \item \textbf{Priorité à l'ordre} : si deux règles reconnaissent la même longueur, c'est celle écrite en premier qui est choisie.
\end{enumerate}
Un caractère qu'aucune règle ne reconnaît est simplement recopié sur la sortie (action par défaut \texttt{ECHO}).
\end{idee}

Le texte reconnu est disponible dans la variable \texttt{yytext}. La chaîne de compilation est :

\begin{code}
flex exercice.l            (produit lex.yy.c)
gcc lex.yy.c -o exercice   (compile l'analyseur)
./exercice < fichier.txt   (l'exécute sur un fichier)
\end{code}

\section{Exercice 1.1 : programme source d'un langage simple}

Texte de test utilisé (fichier \texttt{0.dat}) :
\begin{code}
for( i=0; i < 10; i++ ) {
  truc[i] = 0;
  machin = 12.3;
  bidule = .0;
}
\end{code}

\subsection{a) Reconnaissance de symboles}

La spécification demandée est une seule règle :
\begin{code}
[a-zA-Z][a-zA-Z0-9]*     { printf("<%s> ", yytext); }
\end{code}

\paragraph{Explication du résultat.}
La règle reconnaît tout mot qui commence par une lettre suivie de lettres ou de chiffres, et
l'affiche entre chevrons. Tout le reste est recopié tel quel par Flex :

\begin{center}
\begin{tabular}{>{\ttfamily}l >{\ttfamily}l}
\toprule
\textbf{\color{navy}Entrée} & \textbf{\color{navy}Sortie} \\
\midrule
for( i=0; i < 10; i++ ) \{ & <for>( <i>=0; <i> < 10; <i>++ ) \{ \\
truc[i] = 0;               & <truc>[<i>] = 0; \\
machin = 12.3;             & <machin> = 12.3; \\
bidule = .0;               & <bidule> = .0; \\
\bottomrule
\end{tabular}
\end{center}

Les nombres \texttt{10}, \texttt{12.3} et \texttt{.0} ne sont pas reconnus car ils ne commencent
pas par une lettre. On remarque aussi que \texttt{for} est traité comme un simple identificateur :
rien ne le distingue encore des autres mots. C'est ce que corrige la question suivante.

\subsection{b1) Mots-clés, opérateurs et symboles}

On sépare maintenant trois catégories : mots-clés, symboles (identificateurs) et opérateurs.
\begin{code}
for|while|if|else|do|int|float|char|return|...   { printf("<MOT-CLE:%s> ", yytext); }
[a-zA-Z][a-zA-Z0-9]*                             { printf("<SYMBOLE:%s> ", yytext); }
"++"|"--"|"=="|"!="|"<="|">="|"&&"|"||"|...      { printf("<OPERATEUR:%s> ", yytext); }
[-+*/%=<>!&|^~]  et  [(){}\[\];,.:]              { printf("<OPERATEUR:%s> ", yytext); }
\end{code}

\begin{idee}[Pourquoi l'ordre des règles compte]
Le mot \texttt{for} est reconnu à la fois par la règle des mots-clés et par celle des symboles,
avec la même longueur. C'est la priorité à l'ordre qui tranche : la règle des mots-clés doit donc
être placée \emph{avant}. De même, \texttt{++} est reconnu comme un seul opérateur et non comme
deux \texttt{+}, parce que la règle à deux caractères donne la plus longue correspondance.
\end{idee}

Sur \code{for( i=0; i < 10; i++ )}, on obtient :
\code{<MOT-CLE:for> <OPERATEUR:(> <SYMBOLE:i> <OPERATEUR:=> 0 ...}. À ce stade les nombres sont
encore recopiés sans traitement.

\subsection{b2) Valeurs numériques}

On ajoute deux règles : les entiers et les flottants (avec exposant éventuel).
\begin{code}
EXP     [eE][-+]?[0-9]+
[0-9]+                                                 { printf("<ENTIER:%s> ", yytext); }
[0-9]+"."[0-9]*({EXP})?|"."[0-9]+({EXP})?|[0-9]+{EXP}  { printf("<FLOTTANT:%s> ", yytext); }
\end{code}

Un flottant peut s'écrire \texttt{12.3}, \texttt{12.}, \texttt{.0} ou \texttt{1e5}.
Sur \texttt{12.3}, la règle des flottants (4 caractères) l'emporte sur celle des entiers
(\texttt{12}, 2 caractères) : c'est encore la plus longue correspondance.

\begin{center}
\begin{tabular}{>{\ttfamily}l >{\ttfamily}l}
\toprule
\textbf{\color{navy}Entrée} & \textbf{\color{navy}Sortie} \\
\midrule
machin = 12.3; & <SYMBOLE:machin> <OPERATEUR:=> <FLOTTANT:12.3> <OPERATEUR:;> \\
bidule = .0;   & <SYMBOLE:bidule> <OPERATEUR:=> <FLOTTANT:.0> <OPERATEUR:;> \\
i++            & <SYMBOLE:i> <OPERATEUR:++> \\
\bottomrule
\end{tabular}
\end{center}

\section{Exercice 1.2 : suppression des commentaires C}

Il s'agit de supprimer les commentaires \texttt{/* ... */}, qui peuvent s'étendre sur plusieurs
lignes. Une seule expression régulière serait possible, mais lourde et peu lisible. On utilise
plutôt une \textbf{condition de départ} de Flex, qui joue le rôle d'un état de l'analyseur.

\begin{code}
%x COMMENT
%{ int nb_comm = 0, nb_lignes = 0; %}
%%
\"([^"\\\n]|\\.)*\"    { ECHO; }
"/*"                   { BEGIN(COMMENT); nb_comm++; }
<COMMENT>"*/"          { BEGIN(INITIAL); }
<COMMENT>\n            { nb_lignes++; }
<COMMENT>.             { /* on ignore */ }
<COMMENT><<EOF>>       { fprintf(stderr, "commentaire non termine\n"); return 0; }
\end{code}

\begin{center}
\begin{tikzpicture}[>=stealth, node distance=6cm, every node/.style={font=\small}]
  \node[draw=azur, fill=ciel, rounded corners, minimum width=2.6cm, minimum height=1cm] (n) {état normal};
  \node[draw=navy, fill=navy!15, rounded corners, minimum width=2.6cm, minimum height=1cm, right of=n] (c) {état COMMENT};
  \draw[->, thick, azur] (n.north) to[bend left=25] node[above] {\texttt{/*}} (c.north);
  \draw[->, thick, azur] (c.south) to[bend left=25] node[below] {\texttt{*/}} (n.south);
  \node[below=0.25cm of n, text=navy] {on recopie};
  \node[below=0.25cm of c, text=navy] {on ignore tout};
\end{tikzpicture}
\end{center}

\paragraph{Logique.}
\begin{itemize}[leftmargin=1.5em]
  \item En état normal, le texte est recopié. La lecture de \texttt{/*} fait passer dans l'état \texttt{COMMENT}.
  \item Dans cet état, tous les caractères sont ignorés, y compris les retours à la ligne ; seul \texttt{*/} ramène à l'état normal. Cela gère naturellement les commentaires multi-lignes.
  \item \textbf{Variables dans les actions} : \texttt{nb\_comm} et \texttt{nb\_lignes} sont de simples variables C, modifiées dans les actions et affichées par \texttt{main} à la fin.
  \item La règle sur les chaînes \texttt{"..."} évite de supprimer à tort un \texttt{/*} situé dans un texte, par exemple \texttt{printf("a /* b */ c")}.
  \item Si le fichier se termine en plein commentaire, la règle \texttt{<<EOF>>} signale l'erreur.
\end{itemize}

Sur le fichier de test, 3 commentaires sont supprimés (dont un sur plusieurs lignes) et la
chaîne qui contient un faux commentaire reste intacte.

\section{Exercice 1.3 : expressions régulières}

Quatre analyseurs reconnaissent chacun un langage. Les hypothèses du sujet sont respectées :
un seul mot par ligne, les délimiteurs (espace, tabulation, fin de ligne) sont simplement
recopiés, et une règle « attrape-tout » signale chaque caractère d'un mot non reconnu.

\begin{code}
\n         { ECHO; }
[ \t]      { ECHO; }
^ ER $     { printf("%s  -> ACCEPTE", yytext); }
.          { printf("<?%c>", yytext[0]); }
\end{code}

\begin{idee}[Pourquoi ancrer avec \texttt{\textasciicircum} et \texttt{\$} ?]
Sans ancrage, Flex pourrait reconnaître seulement un \emph{morceau} du mot. Exemple pour le
langage c) : dans \texttt{abba}, le morceau final \texttt{ba} est valide et serait accepté à tort.
En imposant le début (\texttt{\textasciicircum}) et la fin de ligne (\texttt{\$}), on vérifie le mot entier.
\end{idee}

\subsection{a) Les cinq voyelles dans l'ordre}
\begin{code}
^{L}*[aA]{L}*[eE]{L}*[iI]{L}*[oO]{L}*[uU]{L}*$        avec  L = [a-zA-Z]
\end{code}
Les lettres sont libres entre les voyelles, qui doivent seulement apparaître dans l'ordre
$a, e, i, o, u$.

\subsection{b) Mots commençant ou finissant par \texttt{a}}
\begin{code}
^(a[ab]*|[ab]*a)$
\end{code}
Deux cas reliés par \texttt{|} : un \texttt{a} suivi de n'importe quoi, ou n'importe quoi suivi d'un \texttt{a}.

\subsection{c) Pas deux caractères identiques consécutifs}
\begin{code}
^((ab)+a?|(ba)+b?|a|b)$
\end{code}
Si deux lettres voisines sont toujours différentes, le mot \emph{alterne} : \texttt{abab\ldots} ou
\texttt{baba\ldots}. On écrit ces deux familles avec une lettre finale facultative, plus les mots d'une lettre.

\subsection{d) Mots sans la sous-chaîne \texttt{aba}}
\begin{code}
^(b+)?(a+bb+)*(a+b?)?$
\end{code}
C'est l'expression la moins évidente. Interdire \texttt{aba} revient à interdire un \textbf{seul}
\texttt{b} entre deux \texttt{a}. Donc tout bloc de \texttt{b} placé entre deux blocs de \texttt{a}
doit en contenir au moins deux. Le mot se découpe ainsi :
\begin{enumerate}[leftmargin=1.5em]
  \item des \texttt{b} au début, éventuellement : \code{(b+)?} ;
  \item des groupes « un bloc de \texttt{a}, puis au moins deux \texttt{b} » : \code{(a+bb+)*} ;
  \item un dernier bloc de \texttt{a}, éventuellement suivi d'un seul \texttt{b} (permis car rien ne suit) : \code{(a+b?)?}.
\end{enumerate}

\subsection{Résultats des tests}

\begin{center}
\small
\begin{tabular}{l >{\ttfamily}p{5.2cm} >{\ttfamily}p{5.2cm}}
\toprule
\textbf{\color{navy}Langage} & \textbf{\color{navy}\normalfont\bfseries Mots acceptés} & \textbf{\color{navy}\normalfont\bfseries Mots rejetés} \\
\midrule
a) voyelles  & abstemious, facetious, aeiou, AEIOU & sequoia, banane, education \\
b) a au bord & a, ab, ba, abb, aba, abbb, bba      & b, bab, bbb \\
c) alternés  & a, b, ab, abab, baba, babab         & abba, bb, aab \\
d) sans aba  & a, b, ab, abba, bbaa, abb, bbabb, aabba & aba, abab, baba, bab, abaa \\
\bottomrule
\end{tabular}
\end{center}

Pour un mot rejeté comme \texttt{abba} dans le langage c), la sortie est \texttt{<?a><?b><?b><?a>} :
la règle attrape-tout signale chaque caractère.

\section{Programme avec menu}

Pour faciliter le test final, \texttt{tp3\_menu.l} regroupe tous les exercices dans un seul
analyseur. Chaque exercice est une condition de départ (\texttt{E11A}, \texttt{E11B1},
\texttt{E11B2}, \texttt{E12}, \texttt{E13A} à \texttt{E13D}) et ses règles sont préfixées par
cette condition, par exemple \code{<E13B>^(a[ab]*|[ab]*a)$}.

Dans \texttt{main}, le programme :
\begin{enumerate}[leftmargin=1.5em]
  \item affiche le menu et lit le choix de l'utilisateur ;
  \item charge le texte, soit depuis un fichier, soit depuis une saisie au clavier ;
  \item confie ce texte à l'analyseur avec \code{yy_scan_string} ;
  \item active l'exercice choisi avec \code{BEGIN(condition)}, puis appelle \code{yylex()}.
\end{enumerate}

Le texte est nettoyé avant l'analyse (suppression des \texttt{\textbackslash r} des fichiers Windows,
ajout d'un retour à la ligne final) afin que les règles ancrées en fin de ligne fonctionnent
toujours.

\section{Difficultés rencontrées}

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Mots acceptés à tort} (exercice 1.3) : sans ancrage, un morceau de mot était reconnu. L'ancrage par \texttt{\textasciicircum} et \texttt{\$} règle le problème.
  \item \textbf{Fichiers Windows} : les retours à la ligne \texttt{\textbackslash r\textbackslash n} empêchaient la reconnaissance de fin de ligne ; on les supprime avant l'analyse.
  \item \textbf{Commentaires dans les chaînes} (exercice 1.2) : une règle dédiée aux chaînes empêche de les supprimer par erreur.
  \item \textbf{Ordre des règles} (exercice 1.1) : mots-clés avant identificateurs, sinon \texttt{for} serait un simple symbole.
\end{itemize}

\section{Conclusion}

Ce TP a montré qu'une analyse lexicale se ramène à écrire des expressions régulières associées
à des actions en C. Trois notions sont essentielles : la \emph{plus longue correspondance}, la
\emph{priorité par l'ordre des règles} et les \emph{conditions de départ} pour les analyses qui
dépendent du contexte, comme les commentaires. Ces bases serviront directement pour l'analyseur
lexical d'un vrai compilateur.
